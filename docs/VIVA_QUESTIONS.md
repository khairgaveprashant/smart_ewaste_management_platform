## SECTION A: Concept & Problem (Q1–Q5)

### Q1. What is e-waste? Give three examples.

**Answer:**
E-waste (electronic waste) refers to discarded electrical and electronic equipment that has reached the end of its useful life or has been replaced by newer technology.

**Examples:**
1. Mobile phones and smartphones
2. Laptops and desktop computers
3. Televisions, monitors, and other display devices

Other examples include refrigerators, washing machines, printers, batteries, cables, cameras, and remote controls.

---

### Q2. Why is e-waste considered hazardous?

**Answer:**
E-waste contains two types of concerning materials:

**Hazardous substances:**
- **Lead** (in CRT monitors, solder) — damages the nervous system and kidneys.
- **Mercury** (in fluorescent backlights, some switches) — causes neurological damage.
- **Cadmium** (in batteries, semiconductors) — carcinogenic; damages kidneys.
- **Brominated Flame Retardants (BFRs)** — released when burned; cause hormonal disruption.

When e-waste is landfilled or burned, these substances leach into soil and groundwater or are inhaled as toxic fumes — posing serious health and environmental risks, especially for informal recycling workers.

---

### Q3. What is the circular economy? How does E-Cycle implement it?

**Answer:**
The **circular economy** is an economic model designed to eliminate waste and keep resources in use for as long as possible. It contrasts with the **linear economy** (Make → Use → Dispose).

**Circular economy principles:**
- **Reuse**: Use a functional item again directly.
- **Repair**: Fix a broken item to extend its life.
- **Refurbish**: Restore an item to near-new condition.
- **Recycle**: Break down materials and recover raw resources.

**E-Cycle implements this through:**
1. The Segregation Engine — assigns each item to one of four circular pathways.
2. The Circular Economy Workflow — interactive lifecycle diagram showing how items flow through circular stages.
3. The Item Journey Tracker — visualises each registered item's progress through the circular lifecycle.
4. The Economic Value Estimator — demonstrates material recovery value, making circular economy financially tangible.

### Q4. What are the E-Waste Management Rules 2022 (India)?

**Answer:**
The **E-Waste Management Rules, 2022** were notified by India's Ministry of Environment, Forest and Climate Change (MoEFCC). Key provisions include:

- **Extended Producer Responsibility (EPR)**: Manufacturers must collect and recycle a defined percentage of e-waste generated by their products.
- **Authorised collection centres**: E-waste must be channelled to CPCB-authorised dismantlers and recyclers.
- **Prohibited informal disposal**: It is illegal to dump, burn, or dismantle e-waste informally.
- **Targets**: Increasing collection targets year-on-year.

**Relevance to E-Cycle:**
E-Cycle's Collection Registration module supports the spirit of EPR by creating a formal intake record. The Segregation Engine's AUTHORIZED_RECYCLING pathway specifically directs items to authorised recyclers, aligned with legal requirements.

### Q5. What is the global scale of the e-waste problem?

**Answer:**
According to the *Global E-waste Monitor 2024* (UNU/ITU):
- Approximately **62 million tonnes** of e-waste was generated globally in 2023.
- Only **22.3%** was formally collected and recycled.
- E-waste is the **world's fastest-growing solid waste stream**, growing ~2.5 million tonnes per year.
- The formal recycling of e-waste recovered an estimated **USD 28 billion** in raw materials in one year.
- India is one of the **top 5 e-waste generating countries** globally.

## SECTION B: Technical Architecture (Q6–Q12)

### Q6. Why did you use vanilla JavaScript instead of React or Angular?

**Answer:**
We deliberately chose vanilla JavaScript for several reasons:

1. **No dependencies**: The application works with zero npm installs, no build tools, and no Node.js server.
2. **Portability**: The entire application is a single HTML file + CSS + JS — drag it to any browser and it runs.
3. **Learning value**: Building without a framework requires deeper understanding of DOM manipulation, event handling, and state management.
4. **Performance**: No framework overhead — the app loads in milliseconds.
5. **Assessment context**: For a college FA, demonstrating mastery of core web technologies is more appropriate than demonstrating framework usage.

---

### Q7. What is localStorage? How does E-Cycle use it?

**Answer:**
`localStorage` is a browser Web Storage API that allows web pages to store key-value pairs persistently in the browser — data survives page refreshes and browser restarts (unlike `sessionStorage`).

**E-Cycle uses two localStorage keys:**
1. `ecycle_collection_records` — stores all registered e-waste items as a JSON array.
2. `ecycle_rates` — stores the user-configured ₹/kg rates for each device category.

**Data operations:**
- **Save**: `localStorage.setItem(key, JSON.stringify(data))`
- **Load**: `JSON.parse(localStorage.getItem(key))`
- **Clear**: `localStorage.removeItem(key)`

**Limitations acknowledged**: localStorage is single-browser; data is not shared across devices or users.

### Q8. How is the unique collection ID generated?

**Answer:**
Each registered item receives a unique ID in the format:

```
EW-YYYYMMDD-XXXXXX
```

**Algorithm:**
```javascript
function generateCollectionId() {
    const now = new Date();
    const date = now.toISOString().slice(0, 10).replace(/-/g, ''); // YYYYMMDD
    const chars = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789';
    let random = '';
    for (let i = 0; i < 6; i++) {
        random += chars.charAt(Math.floor(Math.random() * chars.length));
    }
    return 'EW-' + date + '-' + random;
}
```

**Components:**
- `EW-` — prefix identifying the E-Cycle system
- `YYYYMMDD` — date-based component (human-readable, sortable)
- `XXXXXX` — 6-character random alphanumeric (collision probability: 1 in 2.18 billion)

### Q9. How does cross-module communication work without a framework?

**Answer:**
All modules communicate through the **Observer/Event pattern** using the browser's built-in Custom Events API.

**How it works:**

1. `storage.js` is the single source of truth for all data.
2. When data changes (add/delete/import), `storage.js` dispatches:
   ```javascript
   document.dispatchEvent(new CustomEvent('ecycle:datachanged'));
   ```
3. Each other module has an event listener:
   ```javascript
   document.addEventListener('ecycle:datachanged', function() {
       // refresh this module's view
   });
   ```

**Benefits:**
- Modules are **decoupled** — `collection.js` doesn't directly call `dashboard.js`.
- Adding a new module only requires adding one event listener — no changes to existing code.
- This pattern is equivalent to what React's state management or Redux achieves, but using only the standard browser API.

### Q10. What is the IIFE pattern and why did you use it?

**Answer:**
**IIFE** stands for **Immediately Invoked Function Expression**. It is a JavaScript pattern where a function is defined and called immediately:

```javascript
(function () {
    'use strict';
    // All code here is private to this module
    var privateVar = 'hidden';

    // Only expose what is needed
    window.ECycleStorage = { save: save, load: load };
})();
```

**Why we used it:**
1. **Encapsulation**: Variables inside the IIFE are not accessible globally — prevents naming conflicts between modules.
2. **No global pollution**: Without `import/export` (which requires a server for ES Modules), IIFEs provide module-like scoping.
3. **`'use strict'`**: Enables strict mode, catching common JavaScript errors at development time.
4. **Selective exposure**: Only the public API is attached to `window` — all internal helpers remain private.

### Q11. How does the application work offline?

**Answer:**
E-Cycle works offline after the initial page load because:

1. **All logic is local**: HTML, CSS, and JavaScript files are loaded from the local filesystem — no API calls to a server.
2. **No runtime network requests**: The application never fetches data from an external URL during normal operation.
3. **localStorage is local**: Data storage is entirely in the browser — no cloud database.

**The only internet dependency** is Google Fonts (Inter typeface) on first load. If offline, the browser falls back to the system sans-serif font — the application remains fully functional, just with a different typeface.

**Practical benefit for the FA**: The demo works reliably even if the venue Wi-Fi is slow or unavailable.

### Q12. How does form validation work in the collection form?

**Answer:**
Form validation uses **client-side JavaScript validation**, not HTML5 `required` attributes alone.

**Validation approach:**
1. On form submit, a `validateForm()` function runs before any data is saved.
2. Each field is checked against specific rules:
   - `deviceType`: must be non-empty
   - `deviceName`: 2–100 characters, non-empty after trimming
   - `quantity`: integer 1–500
   - `weight`: float 0.01–9999
   - `condition`: must be a valid option
3. If any field fails, an error message is inserted adjacent to the field (using `aria-live` for screen reader announcement).
4. The form scrolls to the first error.
5. Only if all fields pass does the registration proceed.

**Security note**: All user-entered values are displayed using `textContent` (not `innerHTML`) to prevent XSS injection.

## SECTION C: Segregation Engine (Q13–Q17)

### Q13. Explain the segregation engine's classification logic.

**Answer:**
The segregation engine in `js/segregation.js` applies a **priority-ordered rule chain** to each registered item:

| Priority | Pathway | Trigger Conditions |
|----------|---------|-------------------|
| 1 (Highest) | SPECIAL_HANDLING | Battery category + damaged/broken condition; OR notes contain keywords: swollen, leaking, bulging, punctured, burning, chemical, mercury |
| 2 | MANUAL_REVIEW | Condition = "Unknown" |
| 3 | REUSE | Condition = "Functional" + device type in [phones, tablets, laptops, printers, desktop] |
| 4 | REPAIR | Condition = "Minor Issues" + device type has repair ecosystem |
| 5 | REFURBISH | Condition = "Major Issues" + device type supports refurbishment |
| 6 (Default) | AUTHORIZED_RECYCLING | All remaining cases (broken/damaged; cables; accessories) |

The chain is evaluated **top-to-bottom** — as soon as a condition matches, that pathway is assigned and evaluation stops.

---

### Q14. Why does SPECIAL_HANDLING take the highest priority?

**Answer:**
**Safety reason**: A damaged, swollen, or leaking lithium-ion battery presents a real fire and explosion risk. If such a battery were accidentally routed to a reuse or repair centre (where staff might not recognise the hazard), it could cause a fire.

**The principle applied is "safety-first"**: No other consideration — not economic value, not device condition, not user preference — can override a safety hazard.

**Implementation detail**: The engine checks for battery-related hazard keywords (`swollen`, `leaking`, `bulging`, `punctured`, `burning`, `chemical`, `mercury`) in the notes field, giving users a way to signal hazards even for device types not normally classified as hazardous.

---

### Q15. What is the difference between REPAIR and REFURBISH pathways?

**Answer:**

| Aspect | REPAIR | REFURBISH |
|--------|--------|-----------|
| **Condition trigger** | Minor Issues | Major Issues |
| **Scope of work** | Fix specific defect (cracked screen, dead battery) | Comprehensive restoration (multiple components, testing, cosmetic) |
| **End result** | Working device; original form | Near-new device; often rebranded or resold |
| **Who does it** | Repair shop; technician | Refurbishment facility; OEM partner |
| **E-Cycle example** | Smartphone with cracked screen → Repair | Laptop with major motherboard issues + cosmetic damage → Refurbish |

Both pathways keep the device in use longer — they extend product life, which is the core goal of the circular economy.

---

### Q16. What happens when a device has condition "Unknown"?

**Answer:**
Items with condition = "Unknown" are assigned to the **MANUAL_REVIEW** pathway.

**Reason**: Without knowing the physical condition of the device, the engine cannot make a safe and accurate classification. Routing an unknown-condition device to REUSE risks sending a broken device to a user. Routing it to REPAIR wastes technician time if the device is actually functional.

**MANUAL_REVIEW means**: A trained technician at the collection centre physically inspects the item, assesses its condition, and re-classifies it into the appropriate pathway.

**This is intentional humility in the algorithm** — the engine acknowledges when it has insufficient data rather than guessing.

---

### Q17. Can the segregation engine be wrong? How would you improve it?

**Answer:**
**Yes**, the engine can be wrong because:
1. It relies on self-reported condition — users may not accurately describe device condition.
2. Keyword detection in notes is based on a fixed list — creative descriptions of damage may be missed.
3. Device sub-model matters — an iPhone 14 and a 10-year-old budget phone have different repair viability.

**Improvements:**
1. **Image recognition** (TensorFlow.js): Upload a photo of the device → neural network assesses visible condition.
2. **Device database lookup**: Model number → manufacturer support status → repair parts availability.
3. **Community feedback**: Recycler or technician confirms classification → used to improve the rule weights.
4. **Condition scoring**: Multi-factor scoring model rather than binary condition categories.

## SECTION D: UI/UX & Accessibility (Q18–Q21)

### Q18. What accessibility features did you implement?

**Answer:**
E-Cycle implements WCAG 2.1 Level AA compliance through:

1. **Semantic HTML**: `<header>`, `<nav>`, `<main>`, `<section>`, `<article>`, `<footer>` — screen readers understand page structure.
2. **Single `<h1>`**: Only the hero section uses `<h1>`; all other headings use `<h2>`–`<h4>` in correct hierarchy.
3. **ARIA attributes**: `role="dialog"`, `aria-modal="true"`, `aria-label`, `aria-expanded`, `aria-controls` on all interactive components.
4. **Keyboard navigation**: Every interactive element is reachable via Tab; modals trap focus; Escape closes modals.
5. **Colour contrast**: All text passes minimum 4.5:1 ratio.
6. **Visible focus rings**: `:focus-visible` CSS shows clear focus indicators.
7. **`prefers-reduced-motion`**: Scroll animations are disabled for users who configure this OS preference.
8. **SVG accessibility**: Decorative SVGs use `aria-hidden="true"`; functional icons have `aria-label`.

### Q19. How does the mobile menu work?

**Answer:**
The mobile menu is a **hamburger menu** that appears on screens narrower than 768px.

**HTML structure**: A `<button id="menuToggle">` with three `<span>` elements (the hamburger lines) toggles a `<div class="mobile-menu">` containing all navigation links.

**JavaScript behaviour (`app.js`):**
- Click toggles `.open` class on the menu and `.active` class on the button.
- `aria-expanded="true/false"` is updated for screen reader announcement.
- `document.body.style.overflow = 'hidden'` prevents background scrolling when menu is open.
- Clicking any menu link calls `closeMobileMenu()`.
- **Escape key** closes the menu and returns focus to the toggle button.

**CSS**: The menu slides in from the top using a CSS transform transition — respects `prefers-reduced-motion`.

### Q20. How did you implement responsive design?

**Answer:**
Responsive design is implemented using **mobile-first CSS** with media queries:

**Base styles (mobile, < 640px):**
- Single-column layouts using Flexbox with `flex-direction: column`.
- Full-width cards and form fields.
- Simplified navigation (hamburger menu).

**Tablet (≥ 640px):**
- Two-column grids for cards.
- Wider form fields.

**Desktop (≥ 1024px):**
- Full horizontal navbar with all links visible.
- Multi-column grids (hero: 2-col; cards: 3–4 col; dashboard: 3 KPI per row).
- Side-by-side layouts for form + preview panels.

**CSS Grid and Flexbox** are used throughout — no float-based layouts.

### Q21. Why did you use CSS Custom Properties (variables)?

**Answer:**
CSS Custom Properties (variables) allow defining reusable values centrally:

```css
:root {
    --color-primary: #1B4332;
    --color-accent: #40916C;
    --fs-base: 1rem;
    --radius-md: 8px;
    --shadow-card: 0 2px 12px rgba(0,0,0,0.08);
}
```

**Benefits:**
1. **Design consistency**: All modules use the same colours, spacing, and typography tokens — impossible to accidentally use the wrong green shade.
2. **Easy theming**: Changing the entire colour scheme requires editing one block of variables, not searching hundreds of CSS rules.
3. **Maintainability**: New team members can understand the design system at a glance.
4. **Runtime updates**: JavaScript can update CSS variables dynamically — e.g., theme switching.

## SECTION E: Data, Testing & Future Scope (Q22–Q25)

### Q22. How does the data export/import feature work?

**Answer:**

**Export:**
1. `ECycleStorage.getAllRecords()` retrieves the full records array from localStorage.
2. It is serialised to `JSON.stringify(data, null, 2)` (pretty-printed).
3. A `Blob` object is created with MIME type `application/json`.
4. An `<a>` element with `href = URL.createObjectURL(blob)` and `download = 'ecycle-records-YYYY-MM-DD.json'` is programmatically clicked.
5. The browser downloads the file — no server involved.

**Import:**
1. User selects a JSON file via `<input type="file">`.
2. `FileReader.readAsText()` reads the file contents.
3. `JSON.parse()` deserialises it; the structure is validated (must be an array; each object must have `id`, `deviceType`, `deviceName`, `condition`, `weight`, `timestamp`).
4. Existing IDs are fetched; any import record whose ID already exists is skipped (duplicate prevention).
5. Valid new records are merged into localStorage.
6. A results notification shows: X added, Y skipped (duplicate), Z errored.

### Q25. What did you learn from building E-Cycle?

**Answer:**
Key learnings:

**Technical:**
1. **Event-driven architecture** scales cleanly — the `ecycle:datachanged` pattern eliminated bugs that would have come from direct module coupling.
2. **Accessibility is not optional** — implementing keyboard navigation and ARIA from the start was easier than retrofitting it. Screen readers exposed layout issues that visual testing missed.
3. **Rule-based logic is powerful when documented** — the segregation engine is transparent and auditable in a way that a black-box ML model cannot be.
4. **Browser APIs are surprisingly capable** — localStorage, FileReader, Custom Events, Blob URL downloads — all without a single npm install.

**Process:**
5. **Incremental development works** — building module by module (Steps 1–10) prevented integration problems.
6. **Testing catches edge cases** — the automated test suite caught a SPECIAL_HANDLING priority bug that manual testing missed.
7. **Design systems save time** — defining CSS variables once and reusing them across 14 sections was far faster than writing ad-hoc styles.

**Domain:**
8. **E-waste has real economic value** — the estimator made us realise how much recoverable material is wasted through informal disposal.
9. **The circular economy is implementable** — even at a software simulation level, the concept is clear and actionable.
